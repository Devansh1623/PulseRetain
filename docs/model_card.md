# Model Card — PulseRetain Attrition Prediction Models

**Version:** 1.0  
**Date:** 2024-12  
**Owner:** PulseRetain Analytics  

---

## Model Overview

| | Details |
|---|---|
| **Task** | Binary classification: predict subscriber attrition (churned = 1) |
| **Primary model** | HistGradientBoostingClassifier (sklearn) |
| **Supporting model** | Wide & Deep Tabular Network (TensorFlow/Keras) |
| **Operating threshold** | 0.40 (tuned to maximise recall; see rationale in README) |
| **Primary metric** | ROC-AUC (threshold-independent); PR-AUC (class-imbalance robust) |

---

## Intended Use

**Intended purpose:**  
Score active SaaS subscribers by attrition probability to prioritise customer success outreach and retention campaigns.

**Primary users:**  
Customer Success Managers, Revenue Operations analysts, VP Customer Success.

**Out-of-scope uses:**  
- Automated account termination decisions
- Employment decisions of any kind
- Any use against individuals (this model operates at the account level)
- Deployment to production without drift monitoring

## Training Data

| | |
|---|---|
| **Source** | Synthetic dataset generated by `src/pulse/ingestion.py` |
| **Size** | ~8,500 accounts (after deduplication) |
| **Period** | Synthetic cohort: 2022-01-01 → 2024-12-31 |
| **Class balance** | ~18% churned (class_weight='balanced' applied) |
| **Splits** | 65% train / 15% validation / 20% test (stratified) |

**Why synthetic?** The IBM Telco dataset (common reference) is not used to avoid licensing concerns and to demonstrate the ability to design a domain-appropriate dataset from scratch. The generator is seeded (seed=42) for full reproducibility.

## Features

See `src/pulse/features.py → FEATURE_CATALOG` for the full list of 25+ features with domain rationale.

**Top feature groups by importance (from permutation importance on GB model):**
1. `payment_failures_12m` — strongest involuntary churn signal
2. `engagement_score` — leading indicator of voluntary churn
3. `billing_annual_flag` — commitment proxy
4. `tenure_log` — habit formation effect
5. `risk_score_simple` — composite heuristic

**Leakage prevention:**
- `churn_probability_true`: dropped before all modelling (it is the generator's latent score — not a real feature)
- `churn_date` and `churn_reason`: dropped (available only after the event)
- `subscription_start_date`: dropped (tenure_months derived from it is used instead)
- Same feature code is used in training and inference

## Evaluation Metrics

| Metric | Why chosen |
|---|---|
| **ROC-AUC** | Threshold-independent ranking ability; standard for imbalanced binary classification |
| **PR-AUC** | Better for imbalanced classes than ROC-AUC; measures precision-recall trade-off |
| **F1 @ 0.40** | Harmonic mean at operating threshold; balances precision and recall |
| **Recall @ 0.40** | Priority metric: catching churners is more valuable than avoiding false alarms |
| **Precision @ 0.40** | Ensures interventions are not wasted on stable accounts |

**Cost-sensitive interpretation:**
- False negative (missed churner): ~$12,000/yr ARR lost (Enterprise account)
- False positive (unnecessary outreach): ~$50 CS cost
- Optimal threshold: lower than 0.50 — we favour recall

## Error Analysis

**Where the models struggle:**
1. **Short-tenure accounts** (< 3 months): limited behavioural signal; predictions are less reliable
2. **Enterprise accounts with low engagement but no payment issues**: ambiguous signal — could be seasonal or a data collection gap
3. **Referral-channel accounts**: different base rate from training distribution; slight precision loss

**Recommendations for error analysis:**
- Examine the predicted probability distribution by plan tier and tenure bucket
- Compare confusion matrix row rates across segments

---

## Limitations

1. **Synthetic data**: distributions are mathematically modelled, not empirical. A model trained on real data would likely show different feature importances.
2. **No temporal validation**: cross-sectional data; a true time-series train/test split would be preferred in production.
3. **No external validation**: no holdout from a different time period or customer population.
4. **Calibration**: probability outputs may not be well-calibrated — a Platt scaling or isotonic regression calibration layer is recommended before using raw probabilities for decision thresholds.
5. **Causal inference absent**: engagement → retention is correlation, not causation.

---

## Fairness and Bias Considerations

The model does not use any demographic features (no gender, age, race, nationality). Features used are purely operational: plan type, billing, engagement, support, and financial metrics.

**Potential indirect biases to monitor:**
- `region` and `industry_vertical` may correlate with protected attributes not present in this dataset. In a production deployment, audit prediction rates by region and industry.
- `acquisition_channel` (e.g. direct_sales vs organic) may reflect the company's own sales targeting biases.

**Recommendation:** Run a fairness audit on real data before production deployment.

---

## Monitoring Suggestions

In production, the following monitoring is recommended:

| Check | Frequency | Alert threshold |
|---|---|---|
| Prediction score distribution (KS test vs training) | Weekly | KS > 0.10 |
| Feature distribution drift (PSI per feature) | Weekly | PSI > 0.20 |
| Actual churn rate vs predicted rate | Monthly | > 5pp gap |
| Model ROC-AUC on labelled data | Quarterly | < 0.75 |

**Retraining trigger:** any of the above alerts fires, or quarterly on schedule.

## Model Versioning

Each training run saves a metadata file at `models/artifacts/{run_id}/metadata.json` containing:
- `trained_at` (ISO timestamp)
- `data_hash` (SHA-256 prefix of training data)
- All evaluation metrics
- Artifact path

Predictions stored in `fact_model_predictions` include `run_id` for traceability.
